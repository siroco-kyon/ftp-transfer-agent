# 取得後の削除方針変更と検証結果

2026-10-02にWindows上で検証した。取得後の削除は一度試し、失敗したファイルはサーバーに残す。失敗したパスと例外を警告ログへ記録し、取得済みのファイルを転送し直したり、次回バッチで削除だけを再開したりしない。

旧方式では、削除再開時に同名の別ファイルを誤って消さないよう、通常の取得でもデータ全体を追加で2回読み取り、削除の進捗をJSONに保存していた。残存ファイルをログで管理する運用に合わせ、追加のハッシュ照合とJSON保存を削除した。通常の転送時のハッシュ照合は維持している。

## 処理の流れ

1. データと必要なENDを取得する。ハッシュ検証が有効なら内容を照合する。
2. ENDを削除する。ENDを削除できなければ、関連するデータも残して警告を記録する。
3. ENDを削除できたらデータの削除を試す。失敗しても取得成功として扱う。

削除だけが失敗した場合は終了コード0となり、エラー通知メールは送らない。転送失敗、ハッシュ不一致、処理の停止・タイムアウトは従来どおり失敗として扱う。接続切断で削除に失敗した接続は再利用せず、後続の転送では接続を作り直す。

ENDがなくなったデータは、`RequireEndFile=true`の次回取得では対象外となる。ENDが残った場合やEND必須でない場合は、次回の通常の取得で再取得する可能性がある。旧版の削除記録は、起動時に残存件数を警告するだけで、記録に基づく自動削除は行わない。

取得中のデータやENDを送り元で同名のまま上書きしない運用を前提とする。本番での削除失敗の頻度は測定していない。

## Windowsの実SFTPサーバーでの確認

Windows上のParamikoサーバーに実際の製品プロセスを接続し、32KiBのデータを取得した。ハッシュ検証とEND取得の有効・無効を組み合わせ、正常削除、データ削除拒否、END削除拒否の12条件を確認した。さらに、ENDが消えてデータだけが残った場合の次回取得を4条件、旧版との比較を2条件実施した。計18条件で想定どおりの結果となった。

削除拒否はサーバーから権限エラーを返して再現した。削除失敗でもローカルのデータは一致し、終了コード0、削除の再試行0回、残存JSON0件だった。失敗した削除は1回だけで、警告ログが残った。END削除拒否ではデータの削除を試していない。

| 通常のハッシュ検証 | 旧版のデータ読み取り量 | 変更後 | 削減した読み取り |
| --- | ---: | ---: | ---: |
| 有効 | 128KiB | 64KiB | データ全体2回分 |
| 無効 | 96KiB | 32KiB | データ全体2回分 |

ハッシュ検証が有効な取得では、SFTPサーバーから読むデータ量が半分になった。これは読み取り量の比較であり、処理時間が半分になるという測定結果ではない。ENDの読み取り量は表に含めていない。

[全18条件の結果](results/results.json)、[製品と旧版の測定条件](results/conditions.json)、[測定時のWorkerソース](results/measured-Worker.cs)、[検証データとサーバーの後始末](results/cleanup.json)を保存している。

測定ログは`results`に保存した。検証用のデータフォルダーは削除済みで、サーバーの待ち受けソケットと全接続も終了している。測定時のソースと結果は証跡として残している。
