背景なぜ既存ツールを作り直すのか

現状: 既存ツール FileTransFTP

社内のファイル連携は、以前から FileTransFTP が担ってきました。長年の実績がある一方で、次の課題を抱えています。

  • .NET Framework 3.5 製で技術基盤が古く（レガシー）、改修や保守が年々難しくなっている
  • 対応プロトコルは FTP / CIFS のみで、SFTP が使えない（CIFS は社内 LAN 向け。外部連携は平文 FTP 一択）
  • 連携先から「SFTP にしてほしい」という要望が来ても応えられない
  • 並列処理がなく、大量ファイル時は 1 件ずつの逐次転送になる

既存ツールを使い続けるリスク

観点リスク
セキュリティFTP は ID・パスワード・データが暗号化されずに流れる。監査・セキュリティ要件で指摘される可能性
社内ルール新規サーバ構築時のセキュリティ基準が厳格化。FTP の利用には「セキュリティ除外申請」が必要になり、構築のたびに申請・承認の負荷がかかる（SFTP なら申請不要）
連携先要件SFTP 必須の連携先と接続できず、新規・更改案件で選択肢を失う
保守性.NET Framework 3.5 等のレガシー基盤のため改修コストが高く、対応できる要員も減っていく
将来性修正のたびにリスクが増し、塩漬けが進むほど移行が難しくなる
「動いているから触らない」を続けるほど、移行コストとリスクは膨らみます。加えて新規サーバではセキュリティ向上のため FTP に除外申請が要る運用になりつつあり、SFTP が使える後継ツールへ計画的に置き換えるのが本提案です。

概要FtpTransferAgent とは何か

現行ツール FileTransFTP の後継。FTP に加えて SFTP に対応し、「正しく送れたこと」の確認まで自動化した転送ツール。
  • 既存ツールの役割（フォルダのファイルを定期転送）はそのまま引き継ぐ
  • .NET 10 製のコンソールアプリ（Windows / Linux / macOS で動作）
  • 起動すると 1 回処理して終了する「バッチ型」（常駐しません）
  • 定期実行はタスクスケジューラ / cron に任せる設計 ─ 運用モデルは従来と同じ

できることマップ

📤 転送の基本

  • アップロード（put） / ダウンロード（get）
  • FTP / SFTP 両対応 + ローカル/UNC 共有
  • ワイルドカードで対象指定（*.csv など）
  • サブフォルダ構造を保ったまま転送
  • 並列転送（最大 16・接続再利用）

🛡️ 信頼性

  • ハッシュ検証（SHA256 / SHA512）
  • 自動リトライ（指数バックオフ）
  • 一時ファイル名 → 完了後リネーム
  • ワーカー隔離（1 件の失敗が他を止めない）

🔧 運用支援

  • END ファイルによる完了判定の連携
  • 転送成功後の自動クリーンアップ
  • 複数宛先への同時配信 + 配信トラッキング（put）
  • 二重起動防止（ロックファイル）

📊 監視・証跡

  • ローリングファイルログ（保持日数指定可）
  • エラー時のメール通知
  • 終了コードでジョブ監視と連携

既存ツールとの比較

観点FileTransFTP（既存）FtpTransferAgent（新）
対応プロトコルFTP / CIFSFTP + SFTP + ローカル/UNC 共有
セキュリティ平文通信（SFTP 非対応）暗号化・鍵認証・ホスト鍵検証
転送後の確認なし（送信のみ）ハッシュ検証（SHA256/512）
失敗時自動リトライ + メール通知リトライ（指数バックオフ）+ メール通知
並列処理なし（1 件ずつ逐次）最大 16 並列・接続再利用
複数宛先配信対応（再送あり/方式は非公開）ファンアウト + 配信トラッキング（指紋検知・宛先別並列）
技術基盤 / 配置.NET Framework 3.5（レガシー・要ランタイム）.NET 10（現行 LTS）・単一ファイル同梱
案件ごとの違い設定ファイル 1 つ設定ファイル 1 つで吸収
失敗時の「リトライ + メール通知」は両ツールとも備えます。新ツールの主な強化点は SFTP・ハッシュ検証・並列処理・配信トラッキング・単一ファイル配置です。

動作の流れ中で何が起きているのか

実行から終了までの 7 ステップ

「送って終わり」ではなく「検証して終わり」。検証に失敗したファイルは成功扱いになりません。

put と get（転送の向き）

「バッチ型」という設計

FtpTransferAgent は常駐しません。起動 → 処理 → 終了、を毎回繰り返します。

この設計のメリット

  • プロセスが残らないので、メモリリークや「いつの間にか止まっていた」が起きにくい
  • ジョブ管理基盤（JP1 / タスクスケジューラ / cron）にそのまま載る
  • 失敗してもプロセスごとやり直せるので復旧が単純
4

安心して使える理由信頼性・安全性の仕組み

仕組み①: 中途半端なファイルを相手に見せない

転送中のファイルを連携先が誤って処理しないよう、一時ファイル名で転送します。

  • リネームは一瞬で終わる操作なので、「半分だけ書かれた data.csv」は存在しない
  • 連携先には「正式名のファイルだけ処理してください」と伝えればよい
ファイル連携トラブルの定番「転送中ファイルの取り込み事故」を構造的に防ぎます。

仕組み②: ハッシュ検証

「送れた」ではなく「壊れずに送れた」を確認します。

  • アルゴリズムは SHA256 / SHA512 から選択（MD5 は安全性の理由で禁止）
  • 不一致ならそのファイルは失敗扱い → リトライ or エラー通知
  • 検証に通るまで「成功後の削除」は行われない（消してから気づく事故がない）

仕組み③: かしこい自動リトライ

エラーには「待てば直るもの」と「待っても直らないもの」があります。FtpTransferAgent はこれを自動で見分けて振る舞いを変えます。

エラーの種類例動作
一時的なエラーネットワーク瞬断、タイムアウト自動リトライ（間隔を倍々に広げる: 5 秒 → 10 秒 → 20 秒…）
恒久的なエラーパスワード間違い、設定ミス即失敗（無駄なリトライをしない）
  • リトライ回数・間隔は設定で調整可能（既定: 3 回、5 秒から指数バックオフ）
  • 「認証エラーなのに 3 回リトライして相手にアカウントロックをかける」ような事故を防ぐ

仕組み④: セキュリティへの配慮

機能内容
SFTP 対応通信が暗号化される転送方式。社内では SFTP を推奨
秘密鍵認証パスワードより安全な鍵ファイルでのログインに対応
ホスト鍵検証接続先サーバーの「指紋」を照合し、なりすましサーバーを検出
パストラバーサル対策不正なファイルパスでフォルダ外に書き込まれることを防止
起動時の警告平文 FTP 使用時や検証スキップ時に警告を表示
FTP（暗号化なし）も使えますが、起動時に警告が出ます。新規案件では SFTP + 鍵認証 + ホスト鍵検証の組み合わせを標準としてください。
5

便利機能実運用を支える機能

END ファイル制御

ファイル連携の定番プロトコル「データを置き終わったら、目印ファイル（END）を置く」に対応しています。

  • END ファイル自体を転送するか・しないかも選べる
  • 必ず「データ → END」の順で転送（順序を保証するので、受け手も同じ方式を安全に使える）
  • 拡張子は .END .TRG など複数指定可能

複数宛先への同時配信（ファンアウト）

1 つのファイルをメイン宛先 + 追加宛先のすべてへ同時に送信できます（put のみ）。

  • 宛先ごとにプロトコル・認証・並列数を個別設定できる（SFTP と FTP の混在も可）
  • 全宛先に成功したときだけローカルファイルを削除（1 つでも失敗したら消さずに残す）
  • 同じ場所（host/path）へ重複して送る誤設定は起動時に警告
用途例: 本番 + バックアップサイト、複数拠点（大阪 / 東京）への一斉配信。サーバー移設で新旧サーバーへ一時的に二重送信したい、といった用途にも使えます。

宛先がダウンしても「賢く」再送する（配信トラッキング）

複数宛先配信では、どの宛先まで送れたかをファイル単位で記録します。一部の宛先が落ちていても、次回はまだ送れていない宛先にだけ送り直します。

  • 配信済みの宛先へは二重配信しない（重複送信事故を防ぐ）
  • 送信後に元ファイルが差し替わったら指紋（サイズ+更新時刻 / ハッシュ）で検知し、全宛先へ送り直す（静かなデータ欠落を防止）
  • この記録は部分失敗したときだけ作られる ─ 全宛先成功なら追加コストはゼロ

並列処理で「速く・止まらず」送る

大量のファイルも最大 16 並列で同時転送できます（Concurrency）。ただ速いだけでなく、並列でも壊れないことを重視した設計です。

  • ワーカー隔離 ─ 1 ファイルの失敗が他の転送を巻き込まない（失敗分だけエラー記録）
  • 接続の再利用 ─ 1 ファイルごとに繋ぎ直さず接続を使い回し、確立コストを削減
  • 宛先ごとに並列数を指定 ─ 速い宛先は多めに、弱い宛先は控えめに、と個別調整
  • 宛先間が独立 ─ ある宛先が詰まっても、健全な宛先への送信は止まらない

二重起動防止

「5 分おきに実行」していて前回がまだ終わっていなかったら…? → ロックファイル（PID 方式）で自動的に防ぎます。

  • 前回が異常終了（クラッシュ）していた場合は自動で検知してロックを引き継ぐので、運用者がロックファイルを手で消す必要はありません

ログとメール通知

📄 ファイルログ

  • logs/yyyy/MM/ 配下に日次で蓄積
  • サイズ上限で自動ローテーション
  • 保持日数を指定して自動削除可能
  • 転送結果・統計・エラーを全件記録

📧 エラーメール通知

  • エラー発生時に SMTP でメール送信
  • 宛先は複数指定可能
  • 1 回の実行での送信上限あり（大量エラー時にメールが大量送信されるのを防止）

導入と移行使い始めるには・旧ツールからどう切り替えるか

導入はファイル 2 つだけ

サーバーに置くのは基本的にこれだけです。

/opt/ftp-transfer-agent/          ← 任意の配置先
├─ FtpTransferAgent(.exe)         ← 実行ファイル（自己完結ビルド）
└─ appsettings.json               ← 設定ファイル
  • 自己完結ビルドなら、サーバーに .NET のインストールは不要
  • Windows Server / Linux / macOS いずれも可
  • プログラムの修正は不要。案件ごとの違いは設定ファイルだけで吸収
  • 将来 .NET 10 のサポートが終了しても、ターゲットを次期 LTS に変えて再ビルドするだけで移行可能 ─ FileTransFTP の .NET Framework 3.5 のような作り直しは不要
「実行ファイル + 設定 1 枚」というシンプルさが、案件横展開のしやすさにつながっています。

設定ファイルの読み方（全体像）

appsettings.json は役割ごとのセクションに分かれています。

セクション決めること例
Watch何を転送するかフォルダ、拡張子、END 条件
Transferどこへ・どうやって送るかFTP/SFTP、put/get、接続先、並列数
Retry失敗したらどう粘るか回数、間隔
Hashどう検証するかSHA256 / SHA512
Cleanup成功後に消すかどうかローカル削除、リモート削除
Smtp障害を誰に知らせるか通知先メールアドレス
Logging記録をどう残すかログパス、保持日数

設定例: 最小構成（FTP アップロード）

{
  "Watch":    { "Path": "./watch", "AllowedExtensions": [".csv"] },
  "Transfer": {
    "Mode": "ftp",  "Direction": "put",
    "Host": "ftp.example.com", "Port": 21,
    "Username": "user", "Password": "********",
    "RemotePath": "/upload"
  },
  "Retry":    { "MaxAttempts": 3, "DelaySeconds": 5 },
  "Hash":     { "Enabled": true, "Algorithm": "SHA256" }
}
./watch フォルダの CSV を /upload へ送り、SHA256 で検証。失敗したら 5 秒 → 10 秒 → 20 秒の間隔で 3 回までリトライします。

設定例: 推奨構成（SFTP + 鍵認証）

{
  "Transfer": {
    "Mode": "sftp", "Direction": "put",
    "Host": "sftp.example.com", "Port": 22,
    "Username": "user",
    "PrivateKeyPath": "./id_ed25519",
    "HostKeyFingerprint": "SHA256:ohD8VZEXGWo6Ez8GSEJQ9Wpafg...",
    "RemotePath": "/in"
  }
}

新規案件はこの形を標準に:

  • Mode: sftp … 通信を暗号化
  • PrivateKeyPath … パスワードではなく秘密鍵で認証
  • HostKeyFingerprint … 接続先が本物のサーバーか検証（なりすまし対策）

定期実行の設定

バッチ型なので、OS のスケジューラに登録して動かします。

Windows（タスクスケジューラ）

schtasks /create /tn "FtpTransferAgent" `
  /tr "C:\opt\FtpTransferAgent\FtpTransferAgent.exe" /sc minute /mo 5

Linux（cron）─ 5 分おきの例

*/5 * * * * /opt/ftp-transfer-agent/FtpTransferAgent

運用時の監視ポイント

ジョブ管理基盤からは終了コードで成否を判定できます。

終了コード意味対応
0全件成功（または対象なし）対応不要
1設定エラー、または転送失敗ありログを確認して原因対応
2二重起動を検出してスキップ頻発するなら実行間隔を見直し

日常の確認はこの 3 点です。

  1. ジョブの終了コード（ジョブ管理基盤のアラート）
  2. エラー通知メール（Smtp 有効時）
  3. ログファイル（logs/yyyy/MM/ 配下）

旧ツールからの移行の進め方（案）

転送経路（送り先・ポート・パス）は変えず、動かすツールだけを差し替える移行です。経路が変わらないので一斉切り替えは不要 ─ 影響の小さい連携から 1 件ずつ、様子を見ながら広げられます。

  • 運用モデル（スケジューラ起動のバッチ）は従来と同じなので、変更は起動コマンドの差し替えが中心
  • まず FTP のまま置き換え、SFTP 化は連携先と調整がついた案件から（この時だけ経路が変わる）

導入前チェックリスト

案件を移行する前に、連携先と以下を確認してください。この 8 項目が決まれば、設定ファイルはほぼ書けます。

  • 転送方式は FTP / SFTP / ローカル（UNC 共有）のどれか（外部連携は SFTP 推奨。旧 CIFS 用途はローカル/UNC 宛先で代替）
  • 認証はパスワードか秘密鍵か
  • 転送方向は put か get か
  • 対象ファイルの命名規則・拡張子
  • END ファイル運用の有無（拡張子は何か、誰が消すか）
  • 転送成功後に元ファイルを消すか残すか
  • 実行間隔（何分おきか、業務時間帯の制約）
  • 障害時の通知先メールアドレス

注意点とまとめ

注意①: 同名ファイルの上書き衝突

唯一の「事故りやすい設定」なので必ず押さえてください。

対策（どちらか）

  • PreserveFolderStructure: true にしてフォルダ構造ごと転送する（推奨）
  • 全ファイルで名前が重複しない命名規約にする
この組み合わせは起動時の設定チェックで検出され、実行前に止まります。

注意②: 向いていない用途

FtpTransferAgent は万能ではありません。以下は別の手段を検討してください。

用途理由 / 代替
リアルタイム同期（秒単位）バッチ型のため。→ 常駐型の同期ツール
双方向同期・競合解決一方向転送が前提。→ 専用同期製品
人が画面で操作する転送CLI ツールのため。→ WinSCP 等の GUI
HTTP/API でのデータ連携FTP/SFTP 専用。→ API 連携基盤
「フォルダに置かれたファイルを、決まった相手に、定期的に、確実に送る」という用途に特化したツールです。

品質面の裏付け

  • 自動テストを完備: 単体テストに加え、実際の FTP / SFTP サーバーを立てた統合テスト（本体を通したエンドツーエンド検証）
  • ネットワーク障害・ファイルロック・並列実行・複数宛先配信などの異常系テストを含む
  • CI（GitHub Actions）で全テスト + コード整形チェックを毎回実行
  • 実績ある OSS ライブラリを採用（FluentFTP / SSH.NET / Polly）

まとめ

FtpTransferAgent は、レガシー化した既存ツール FileTransFTP の後継です。
  • 置き換えの最大の動機は SFTP 対応（セキュリティ・連携先要件への対応）
  • 単なる移植ではなく、検証・リトライ・完了判定・証跡も併せて強化
  • 運用モデル（スケジューラ起動のバッチ）は従来と同じなので、移行の負担は小さい
  • 設定ファイル 1 枚で案件ごとの違いを吸収 → 段階的な置き換えがしやすい

移行で押さえる 3 点

  1. 案件単位の段階的置き換え（並行稼働 → 突き合わせ → 切り替え）
  2. 新規・更改案件は SFTP + 鍵認証 + ホスト鍵検証を標準にする

付録 B: 用語集

用語意味
FTP / SFTPファイル転送の通信方式。SFTP は暗号化あり（SSH ベース）で安全
CIFSWindows のファイル共有プロトコル（SMB）。主に社内 LAN 向けで、外部連携や暗号化用途には不向き
put / getput = こちらから送る（アップロード）、get = 取りに行く（ダウンロード）
ハッシュ値ファイル内容から計算される「指紋」。1 ビットでも違えば値が変わる
END ファイル「データを置き終わった」ことを示す目印ファイル。トリガーファイルとも呼ぶ
ファンアウト1 つのファイルを複数の宛先へ同時に配信すること（put のみ）
配信トラッキング複数宛先配信で「どのファイルをどの宛先まで送れたか」を記録し、未配信の宛先だけ再送する仕組み
並列転送 / Concurrency複数ファイルを同時に処理する数（1〜16）。1 件の失敗は他に波及しない（ワーカー隔離）
指数バックオフリトライ間隔を 5 秒 → 10 秒 → 20 秒のように倍々に広げる方式
バッチ型常駐せず、起動のたびに 1 回処理して終了する動作モデル
終了コードプログラムが終了時に返す数値。0 = 正常、それ以外 = 異常
ロックファイル「実行中」の目印ファイル。二重起動の防止に使う
.NET Framework / .NET 10アプリの実行基盤。Framework 3.5 は Windows 専用のレガシー。.NET 10 はクロスプラットフォームの現行 LTS（2028 年まで）で、次期 LTS への移行も再ビルドで済む
単一ファイル（self-contained）ランタイムを同梱して 1 つの実行ファイルにまとめた配布形態。サーバーに .NET を入れなくても動く
