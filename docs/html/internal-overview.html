背景と置き換えの必要性なぜ現行ツールを作り直すのか

1.1 現行ツールが抱える課題

社内のファイル連携は長年 FileTransFTP が担ってきましたが、次の課題により、新規案件・更改案件への適用が難しくなっています。

課題現状放置した場合の影響
SFTP 非対応対応プロトコルは FTP / CIFS のみ。外部連携は平文 FTP に限られるSFTP を必須とする連携先と接続できず、案件自体を受注できない
セキュリティID・パスワード・データが暗号化されずに流れる監査・セキュリティ点検での指摘対象になる
社内基準新規サーバー構築時の基準が厳格化し、FTP の利用には除外申請が必要構築のたびに申請・承認の負荷が発生する（SFTP なら申請不要）
保守性.NET Framework 3.5 製で技術基盤が古い改修コストが上がり続け、対応できる要員も減っていく
性能並列処理がなく、1 件ずつの逐次転送ファイル件数の増加に比例して転送時間が伸びる
現行ツールを使い続けるほど移行コストは増え、その間も SFTP 必須の案件を取りこぼし続けます。後継ツールへ計画的に置き換えることをご提案します。

1.2 現行ツールとの機能比較

観点FileTransFTP（現行）FtpTransferAgent（新）
対応プロトコルFTP / CIFSFTP / SFTP / ローカル・UNC 共有
通信の暗号化なし（平文のみ）SFTP により暗号化。鍵認証・ホスト鍵検証にも対応
転送後の確認なし（送信のみ）ハッシュ検証（SHA256 / SHA512）
失敗時の動作自動再試行 + メール通知自動再試行（指数バックオフ）+ メール通知
並列転送なし（1 件ずつ逐次）最大 16 並列。接続を再利用する
複数宛先への配信対応（再送の方式は非公開）ファンアウト + 配信トラッキング（未配信の宛先だけ再送）
技術基盤.NET Framework 3.5（Windows 専用・レガシー）.NET 10（現行 LTS・クロスプラットフォーム）
サーバーへの配置ランタイムの導入が必要実行ファイルと設定ファイルの 2 つのみ（ランタイム同梱）

失敗時の再試行とメール通知は現行ツールも備えています。今回の主な強化点は SFTP 対応・ハッシュ検証・並列転送・配信トラッキング・配置の簡素化の 5 点です。

1.3 置き換えの基本方針

  • 転送経路（接続先・ポート・パス）は変更せず、実行するツールだけを差し替える
  • そのため一斉切り替えは不要で、影響の小さい連携から 1 件ずつ移行できる
  • 運用モデル（スケジューラからのバッチ起動）も従来どおりのため、運用手順の変更は最小限で済む
  • SFTP 化は連携先との調整がついた案件から段階的に実施する（このときだけ経路が変わる）

適用範囲（スコープ）何に使い、何には使わないか

「フォルダに置かれたファイルを、決まった相手へ、定期的に、確実に送る（受け取る）」用途に特化したツールです。
対象とする用途対象外とする用途（別手段を検討）
  • 他システムとの定時ファイル連携（put / get）
  • 夜間バッチ・数分間隔の定期転送
  • 「データ本体 + 完了通知（END）ファイル」形式の受け渡し
  • 同一ファイルの複数拠点への一斉配信
  • 社内共有フォルダ（UNC / SMB）への書き込み（現行の CIFS 用途の置き換え）
  • 秒単位のリアルタイム同期 → 常駐型の同期ツール
  • 双方向同期・競合解決 → 専用の同期製品
  • 人が画面で操作する転送 → WinSCP 等の GUI ツール
  • HTTP / API でのデータ連携 → API 連携基盤

動作環境

  • Windows Server / Linux / macOS（.NET 10 ベース）
  • 自己完結ビルドで配布するため、サーバーへの .NET のインストールは不要
  • サーバーに配置するのは実行ファイルと設定ファイル appsettings.json の 2 つのみ
  • 案件ごとの違いはすべて設定ファイルで対応する（プログラムの個別改修は不要）

3.4 複数宛先への配信（ファンアウト）

1 つのファイルをメイン宛先と追加宛先のすべてへ同時に送信できます（put のみ）。宛先ごとにプロトコル・認証・並列数を個別に設定でき、SFTP と FTP を混在させることもできます。

一部の宛先だけ失敗した場合は、どの宛先まで送れたかをファイル単位で記録し、次回の実行ではまだ送れていない宛先にだけ送り直します（配信トラッキング）。

  • 全宛先に成功したときだけ元ファイルを削除する。1 つでも失敗した場合は削除せずに残す
  • 配信済みの宛先へは二重に配信しない
  • 送信後に元ファイルが差し替わった場合は指紋（サイズ + 更新時刻、またはハッシュ）で検知し、全宛先へ送り直す
  • この記録は一部の宛先が失敗したときだけ作成されるため、全宛先に成功した場合の追加コストは発生しない
  • 同じ接続先の同じパスへ重複して送る誤設定は、起動時に警告する
サーバーの移設時に、新旧のサーバーへ一時的に二重送信したい場合にも利用できます。

信頼性・セキュリティ仕様「確実に届いた」をどう担保するか

4.1 転送の確実性

仕組み仕様
一時名 → リネーム転送中は一時ファイル名を使い、完了後に正式名へリネームする。リネームは一瞬で完了するため、書きかけのファイルを相手のバッチが取り込む事故が構造的に起きない
ハッシュ検証
（任意・経路によって推奨が異なる）		SHA256 ／ SHA512 で送信元と送信先の内容の同一性を確認する（MD5 は安全性の理由により選択できない）。不一致であればそのファイルは失敗として扱い、成功後の削除は行わない。SFTP では通信路自体が HMAC で完全性を保証するため、ハッシュ検証は無効での運用を推奨する（下の補足を参照）
自動再試行ネットワークの瞬断やタイムアウトなど、一時的なエラーだけ再試行する（既定 3 回、5 秒 → 10 秒 → 20 秒の指数バックオフ）
再試行しない判定認証の失敗や設定の不備など、待っても直らないエラーは即座に失敗とする。連携先のアカウントロックを誘発しない
ワーカー隔離並列転送中に 1 件が失敗しても、他のファイルや他の宛先への転送は継続する
ハッシュ検証は「必須」ではなく、通信経路に応じて有効・無効を選ぶ設定項目です。
SFTP（SSH）では、通信路そのものがパケット 1 つごとに HMAC（改ざん・破損の検知符号）で保護されています。途中でデータが 1 ビットでも化ければ検知され、通信自体がエラーとして中断されます。加えて、サーバーへの書き込みが成功したかどうかも 1 回ごとに応答で確認しています。つまり内容の同一性は転送レイヤーですでに担保されており、ハッシュ検証はその上に重ねる二重確認になります。
一方でハッシュ検証を有効にすると、送信したファイルを照合のために相手側から全量読み戻すため、ネットワーク転送量がおよそ 2 倍になり、大容量ファイルでは所要時間に直接響きます。得られる追加の保証に対して代償が大きいため、SFTP 経路ではハッシュ検証を無効にする運用を推奨します。
経路転送レイヤーの完全性保証ハッシュ検証の推奨
SFTPパケットごとの HMAC ＋ 書き込み応答の確認無効を推奨（保証が重複し、転送量が 2 倍になるだけのため）
FTPTCP チェックサム（16 ビット）のみ有効を推奨（転送レイヤーの保護が弱いため、内容の確認はハッシュに頼る）
ファイルサーバー
（SMB 共有）		環境設定に依存（SMB 署名の有無による）配置先の設定が確認できない場合は有効を推奨

項目仕様
通信の暗号化SFTP（SSH ベース）に対応する。社内標準は SFTP とする

運用仕様どう動かし、どう監視するか

5.1 実行方式

常駐せず、起動 → 処理 → 終了を毎回繰り返すバッチ型です。定期的な実行は OS のスケジューラに任せます。

# Windows（タスクスケジューラ・5 分間隔）
schtasks /create /tn "FtpTransferAgent" /sc minute /mo 5 ^
  /tr "C:\opt\FtpTransferAgent\FtpTransferAgent.exe"

# Linux（cron・5 分間隔）
*/5 * * * * /opt/ftp-transfer-agent/FtpTransferAgent
  • 常駐しないため、メモリリークや、停止に気づかないまま放置される事態が起きにくい
  • 既存のジョブ管理基盤（JP1 / タスクスケジューラ / cron）にそのまま載せられる
  • 前回の実行が終わっていない場合は二重起動を防止し、何もせず終了コード 2 で終了する

5.2 監視方法

ジョブ管理基盤からは終了コードで成否を判定します。

終了コード意味運用対応
0全件成功（対象ファイルがない場合を含む）対応不要
1設定エラー、または 1 件以上の転送失敗ログを確認して原因に対応する
2二重起動を検出してスキップ頻発する場合は実行間隔を見直す

日常の確認は次の 3 点です。

  1. ジョブの終了コード（ジョブ管理基盤のアラート）
  2. エラー通知メール（SMTP 有効時）
  3. ログファイル（logs/yyyy/MM/ 配下）

5.3 移行時に連携先と確認する項目

案件を移行する際は、次の 8 項目を確認します。これらが決まれば設定ファイルを作成できます。

  • 転送方式（FTP / SFTP / ローカル・UNC 共有のいずれか。外部連携は SFTP を推奨）
  • 認証方式（パスワード / 秘密鍵）
  • 転送方向（put / get）
  • 対象ファイルの命名規則と拡張子
  • END ファイル運用の有無（拡張子、削除する担当者）
  • 転送の成功後に元ファイルを削除するか、保持するか
  • 実行間隔（何分間隔か、業務時間帯の制約）
  • 障害時の通知先メールアドレス

制約・リスクと対応方針あらかじめ認識しておく事項

項目内容対応方針
同名ファイルの上書き衝突 サブフォルダを対象にしながらフォルダ構造を維持しない設定にすると、A/result.csv と B/result.csv が同じ宛先パスに集まり、上書きされる 起動時の設定チェックでエラーとして検出し、実行前に停止する。フォルダ構造を維持する設定を標準とする
平文 FTP の残存 移行の初期は、既存の連携が FTP のまま残る まずツールだけを差し替え、SFTP 化は連携先との調整がついた案件から順次実施する
リアルタイム性 バッチ型のため、実行間隔より短い時間で届けることはできない 実行間隔を業務要件に合わせて設定する（分単位まで短縮できる）
資格情報の管理 設定ファイルにパスワードを直接記載すると、設定ファイル自体の取り扱いに注意が必要になる 環境変数による上書き、または鍵認証への切り替えを推奨する
技術基盤の更新 .NET 10 も将来はサポートが終了する 次期 LTS を対象に再ビルドするだけで移行できる。現行ツールのような作り直しは発生しない

品質の担保

  • 単体テストに加え、実際の FTP / SFTP サーバーを立てた統合テスト（本体を通したエンドツーエンドの検証）を実施している
  • ネットワーク障害・ファイルロック・並列実行・複数宛先への配信など、異常系のテストを含む
  • CI（GitHub Actions）で全テストとコード整形のチェックを毎回実行している
  • 転送処理には実績のある OSS ライブラリ（FluentFTP / SSH.NET / Polly）を採用している

導入スケジュール（案）承認から全案件の移行完了まで

付録 B. 用語

用語意味
FTP / SFTPファイル転送の通信方式。SFTP は SSH をベースとしており、通信が暗号化される
CIFS / SMBWindows のファイル共有プロトコル。社内 LAN 向けで、外部との連携には向かない
put / getput はこちらから送ること（送信）、get は取りに行くこと（受信）
ハッシュ値ファイルの内容から計算される「指紋」。1 ビットでも異なれば値が変わる
END ファイル「データを置き終わった」ことを示す目印のファイル。トリガーファイルとも呼ぶ
ファンアウト1 つのファイルを複数の宛先へ同時に配信すること（put のみ）
配信トラッキングどのファイルをどの宛先まで送れたかを記録し、未配信の宛先だけへ再送する仕組み
指数バックオフ再試行の間隔を 5 秒 → 10 秒 → 20 秒のように倍々に広げる方式
バッチ型常駐せず、起動のたびに 1 回だけ処理して終了する動作モデル
終了コードプログラムが終了時に返す数値。0 は正常、それ以外は異常を示す
自己完結ビルド実行環境（ランタイム）を同梱した配布形態。サーバーに .NET を導入せずに動作する
