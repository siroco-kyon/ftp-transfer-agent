結論を先に 3 行で。
  1. SFTP と FTPS は別物です。「FTP を暗号化したもの」が FTPS、「SSH の上でファイルを操作する別プロトコル」が SFTP で、共通点は名前だけです。
  2. 暗号強度そのものに実質的な優劣はありません。差が出るのは、ファイアウォール・鍵/証明書の管理・サーバ実装のばらつきといった運用面です。
  3. 本ツールは SFTP を標準としました。社内基準・連携先の要件・単一ポートで完結する運用性・鍵認証とホスト鍵検証の実装しやすさが理由で、FTPS は現時点で実装していません（5 章・6 章）。

まず用語を整理するFTP / FTPS / SFTP / SCP の関係

この 3 つは名前が似ているため現場でしばしば混同されますが、成り立ちがまったく異なります。ここを取り違えると「SFTP 対応と言われたので FTPS サーバを立てた」といった手戻りが起きます。

呼び方正式名称中身標準
FTPFile Transfer Protocol1971 年から続く暗号化なしのファイル転送プロトコル。ID・パスワード・データがそのままネットワークを流れるRFC 959
FTPSFTP over TLS/SSLFTP をそのまま TLS でくるんだもの。コマンド体系（USER / PASS / PASV / STOR …）は FTP と同一で、通信路だけが暗号化される。HTTP に対する HTTPS と同じ関係RFC 4217 ほか
SFTPSSH File Transfer ProtocolFTP とは無関係の別プロトコル。SSH（サーバへのリモートログインに使う仕組み）の上で動くサブシステムとして、ファイルの読み書き・属性取得を行うIETF ドラフト
（事実上 OpenSSH 実装が標準）
SCPSecure Copy Protocol同じく SSH 上で動くが、単純なコピーのみで一覧取得や再開ができない旧方式。OpenSSH でも現在は内部的に SFTP へ置き換えられている―
「S」の意味が違います。FTPS の S は Secure（TLS で保護された FTP）、SFTP の S は SSH です。
FTPS サーバに SFTP クライアントで接続することはできませんし、その逆もできません。相手先とは必ず「SFTP（SSH・22 番）ですか、FTPS（FTP over TLS・21 番）ですか」と明示的に確認してください。

なお FTPS には接続の開始方法が 2 種類あります。この違いも相手先との確認事項です。

  • Explicit FTPS（明示的、RFC 4217） ─ 通常の FTP と同じ 21 番に平文で接続し、AUTH TLS コマンドで TLS へ切り替える。現在の主流。
  • Implicit FTPS（暗黙的） ─ 990 番に接続した時点で最初から TLS。古い方式で、正式な標準化はされていない。

仕組みの違い何の上に何が載っているか

3 方式を層構造で並べると、FTPS と SFTP が「似て非なるもの」である理由がはっきりします。FTPS は FTP に暗号の層を足したもの、SFTP は SSH の中に間借りしている別のプロトコルです。

FTPS が「FTP をそのまま包む」ということは、FTP が抱えていた構造上のクセ（制御用とデータ用で接続を分ける方式）もそのまま引き継ぐということです。これが次章のファイアウォールの話につながります。

通信経路とファイアウォール運用でいちばん差が出るところ

3.1 FTP／FTPS は接続を 2 本使う

FTP 系は、コマンドをやり取りする制御接続と、ファイルの中身を流すデータ接続を分けます。データ接続はファイル 1 件ごと（一覧取得ごと）に張り直され、そのポート番号は接続のたびにサーバが動的に決めます（パッシブモードの場合）。

そのため FTP/FTPS を通すには、ファイアウォールで 21 番に加えてデータ用のポート範囲（例: 50000〜50100）を開放する必要があります。SFTP は制御もデータも 22 番の 1 本の接続の中で多重化されるため、開けるポートは 22 番だけです。

3.2 FTPS 特有のやっかいごと

  • ファイアウォールの「FTP 支援機能」が効かなくなる ─ 平文 FTP なら、ファイアウォールが PASV の応答（サーバが指定するデータ用ポート番号）を読み取って自動的に穴を開けてくれます。FTPS ではその応答が暗号化されて読めないため、この仕組みが働かず、ポート範囲を静的に開放しておく必要があります。
  • データ接続の TLS セッション再利用 ─ セキュリティ上の理由から、制御接続の TLS セッションをデータ接続でも再利用することを必須とするサーバ実装があります（例: vsftpd の require_ssl_reuse）。クライアント側がこれに対応していないと、認証は通るのにファイル転送だけが失敗するという切り分けの難しい事象になります。
  • 証明書の運用 ─ サーバ証明書の発行・更新・信頼設定が必要です。社内 CA の証明書や自己署名証明書を使う場合は、クライアント側にも信頼設定を配る運用が発生します。
SFTP 側にも相手を確認する仕組みはあり、それがホスト鍵です。証明書と違って有効期限や CA が不要な代わりに、初回接続時に正しい鍵かどうかを利用者が確認するという運用が必要になります。本ツールではこれを設定ファイルで固定できるようにしています（5 章 理由 3）。

本ツールが SFTP を標準とした 6 つの理由FtpTransferAgent の設計判断

本ツールは、旧ツール FileTransFTP（FTP / CIFS のみ対応）の後継として開発されました。新規・更改案件の標準を「SFTP ＋ 鍵認証 ＋ ホスト鍵検証」に置くという方針で設計しており、その根拠は次の 6 点です。

理由 1 ─ 社内基準と連携先の要件が SFTP を求めている

新規サーバ構築時の社内基準が厳格化され、平文 FTP の利用には除外申請と承認が必要になりました。SFTP であれば申請そのものが不要です。加えて、外部連携先から SFTP を必須条件として提示される案件が増えており、旧ツールでは対応できず案件を受けられない状況が発生していました。

ここで重要なのは、相手先が求めているのは「暗号化された FTP」ではなく、名指しで「SFTP」であることが大半という点です。FTPS を実装しても、この要件は満たせません。

根拠: 仕様確認資料 1 章「現行ツールが抱える課題」

理由 2 ─ 開けるポートが 1 つで済み、運用・申請コストが小さい

本ツールは複数の宛先へ同時に配信（ファンアウト）し、最大 16 並列で転送します。FTPS ではこの並列転送のたびにデータ接続が張られるため、ネットワーク申請では余裕を見たポート範囲の開放が必要で、拠点や連携先が増えるたびに同じ調整を繰り返すことになります。

SFTP なら並列度をいくつに上げても開放するのは 22 番だけです。接続の疎通確認も 22 番 1 つを見ればよく、トラブル時の切り分けが容易になります。

根拠: ファンアウトと並列処理 実装詳細 / 本資料 3 章

理由 3 ─ 鍵認証とホスト鍵検証を、ツール側で完結して提供できる

本ツールは SFTP について、次のセキュリティ機能を実装済みです。

  • 公開鍵認証（PrivateKeyPath）─ 設定ファイルにパスワードを置かずに運用できる。起動時に鍵ファイルの存在と読み取り権限を検証し、問題があれば起動を中止する
  • ホスト鍵指紋の照合（HostKeyFingerprint）─ 接続先サーバの指紋を設定に固定し、一致しなければ接続を中断する。中間者攻撃への対策となる。未設定の場合は「検証せずに接続した」旨を警告としてログに残す
  • 脆弱なホスト鍵アルゴリズムの除外 ─ 接続時に ssh-rsa(SHA-1) と ssh-dss を候補から取り除く

FTPS で同等のことをするには、証明書チェーンの検証方針・信頼ストアの扱い・クライアント証明書の配布といった仕組みを別途設計・実装する必要があります。「鍵ファイル 1 つと指紋 1 行」で完結する SFTP のほうが、実装も運用手順書も単純になります。

根拠: Services/SftpClientWrapper.cs（AttachHostKeyValidation）/ Configuration/ConfigurationValidator.cs

理由 4 ─ 転送レイヤーで完全性が担保され、運用を簡素にできる

SSH はパケットごとに HMAC / AEAD による改ざん検知を行い、SFTP は書き込み・クローズ・リネームの各操作に対してサーバからの成功応答を確認します。そのため本ツールでは、SFTP 利用時はハッシュ検証（Hash:Enabled）を無効にした運用を推奨しています。ハッシュ検証は転送のたびに送信元・送信先の両方でファイル全体を読み直すため、無効化できると転送時間とサーバ負荷を大きく削減できます。

アップロードは一時ファイル名で書き込み、完了後にアトミックにリネームする方式です。受信側のバッチが書きかけのファイルを拾う事故を防ぎます。

根拠: SFTP 転送性能の調査レポート §5 / README「ハッシュ検証」節

理由 5 ─ ファイル一覧・属性が構造化されて取れる（get 方向で効く）

FTP / FTPS のファイル一覧は、サーバの種類（UNIX 系・Windows 系・製品固有）によって文字列の書式が異なり、クライアント側で解析する必要があります。日付表記やロケールの違いで誤解析が起きると、ファイルの取りこぼしや二重取得につながります。

SFTP はサイズ・更新日時・種別が構造化されたデータとして返るため、この種の解析起因の不具合が原理的に発生しません。本ツールはダウンロード（Direction: "get"）や、宛先ごとの配信済み判定（サイズ・更新日時による署名）で一覧情報を使うため、この違いは信頼性に直結します。

根拠: 宛先別配信トラッキングのドキュメント

理由 6 ─ 実装・テスト・チューニングを 1 方式に集中できる

本ツールは SFTP について、実測にもとづく性能改善まで作り込んでいます。リモートディレクトリ存在確認のキャッシュ、リネーム後の存在確認を省略するオプション、書き込みバッファサイズの調整などで、高レイテンシ回線において1.4〜1.57 倍の高速化を確認しました（整合性は全ケース SHA256 全数比較で検証済み）。また Docker を用いた SFTP 統合テストも整備しています。

FTPS を追加すると、暗号化モード（明示的／暗黙的）・証明書検証方針・データ接続の TLS セッション再利用といった設定項目とテストの組み合わせが一気に増えます。対応方式を絞ることで、限られた工数を品質と性能に振り向ける判断をしました。

根拠: SFTP 転送性能の調査レポート / README「SFTP 統合テスト（Docker）」節

FTPS を採用しなかった理由と、FTPS が適するケース公平に見た場合の整理

6.1 採用しなかった理由

FTPS はプロトコルとして劣っているわけではありません。採用しなかったのは、次のとおり「本ツールが解決したい課題に対して優先度が低い」という判断です。

観点判断
要件を満たさない連携先や社内基準が求めているのは名指しで「SFTP」であることが大半。FTPS を実装しても、旧ツールが受注できなかった案件は受注できるようにならない
運用コストが減らないデータ用ポート範囲の開放という、FTP 時代からのネットワーク申請の手間が残る。むしろ TLS 化でファイアウォールの FTP 支援機能が効かなくなる分、構成の難易度は上がる
証明書運用が必要になる発行・更新・信頼設定という継続的な作業が発生する。SFTP の鍵・指紋運用に比べて手順書と教育のコストが大きい
相互運用の不確実性データ接続の TLS セッション再利用など、サーバ実装によって成否が分かれる要素があり、事前検証の負担が読みにくい
工数配分対応方式を増やすより、SFTP の性能・信頼性・テストに投資するほうが利用者の便益が大きいと判断（5 章 理由 6）

6.2 それでも FTPS が適するケース

次のような場合は FTPS が合理的です。該当する連携が出てきた場合は、本ツールへの機能追加を個別に検討します。

  • 連携先が FTPS しか提供していない（相手先の都合で選択の余地がない）
  • 既存の FTP 資産を最小の変更で暗号化したい ─ FTPS はコマンド体系が FTP と同一のため、既存のサーバ設定・アカウント・ディレクトリ構成を活かしやすい
  • クライアント証明書による相互認証を、既存の PKI 基盤に乗せて統制したい
  • SSH サーバを立てられない事情がある（22 番の開放や SSH ログインが組織方針で禁止されているなど）
現時点で本ツールは FTPS に対応していません。Mode に指定できるのは ftp（平文）・sftp・local の 3 つで、FTPS 用の設定項目（AUTH TLS の有効化、証明書検証方針など）は用意していません。FTPS が必要な案件が発生した場合は、要件を確認のうえ機能追加として検討します。

SFTP の弱点と本ツールでの対策良いところだけではない

公平を期すため、SFTP を選んだことによる不利な点と、本ツールでの対策も記載します。

SFTP の弱点内容本ツールでの対策
1 ファイルあたりの往復が多い ファイルを 1 件送るのに、パス解決・存在確認・オープン・書き込み・クローズ・リネームと複数回のやり取りが発生する。小さなファイルを大量に送る × 遅い回線、の組み合わせで支配的になる リモートディレクトリ存在確認のキャッシュを常時有効化し、VerifyUploadedFileExists: false でリネーム後の追加確認を省略可能に。往復 10 回 → 6 回に削減し、RTT 10ms 環境で最大 1.57 倍の高速化を実測
並列化しないと遅い 上記の往復コストは 1 本の接続では隠せない Concurrency（1〜16）で並列転送。実測では 16 並列までほぼ線形に短縮する
バッファ拡大の効果が限定的 OpenSSH 系サーバは 32KB のパケット上限を通知するため、BufferSizeKB を上げても効果がない 32KB 超を指定した場合は起動時に警告を表示。上限を 64KB に制限し、送信時例外を防止
サーバ側ハッシュ機能がない FTP の XCRC/XSHA のような拡張が標準にない ハッシュ検証は常にローカル計算で実施。UseServerCommand を SFTP で有効にした場合は警告のうえローカル計算にフォールバック。そもそも SFTP では理由 4 のとおりハッシュ検証を無効にする運用を推奨
上書きリネームが拡張依存 上書きを伴うアトミックリネームは posix-rename@openssh.com 拡張に依存し、非対応サーバでは使えない 非対応サーバでは「削除 → リネーム」へ自動フォールバック。往復は増えるが動作は継続する
小ファイル大量 × WAN の構成では、Concurrency を上げ、VerifyUploadedFileExists: false と Hash:Enabled: false を併用するのが最も効果的です。詳細な指針は SFTP 転送性能の調査レポート §5 チューニングガイド を参照してください。

    "RemotePath": "/upload",
    "Concurrency": 4,
    "VerifyUploadedFileExists": false
  },
  "Hash": {
    "Enabled": false
  }
}
  • Password を書かずに PrivateKeyPath だけで認証できます（設定ファイルに平文パスワードを残さない）
  • HostKeyFingerprint は接続先サーバで ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub を実行して得られる SHA-256 指紋を SHA256: 付きで指定します
  • Hash:Enabled を false にできるのは、SSH が転送レイヤーで改ざん検知を行うためです（5 章 理由 4）
ホスト鍵指紋は、必ず信頼できる経路で入手してください。初回接続時のログに出力された指紋をそのまま設定に写す運用は、その 1 回目が中間者攻撃だった場合に攻撃者の鍵を固定してしまいます。サーバ管理者から別経路（構築手順書・対面・別チャネル）で受け取った値と照合してください。

8.3 やむを得ず平文 FTP を使う場合

  • 相手先が FTP しか提供しておらず、かつ社内の除外申請が承認されている場合に限ります
  • 転送レイヤーに完全性の保証がないため、Hash:Enabled: true によるハッシュ検証の有効化を推奨します。とくに Cleanup:DeleteAfterVerify: true（転送後に元ファイルを削除）と併用する場合は、検証なしでの削除になるため必ず有効にしてください
  • 専用アカウントを用意し、他システムとパスワードを共用しないでください

選定フローと FAQ迷ったときの判断手順

FAQ

Q. 相手先から「FTP を暗号化したい」と言われました。SFTP でよいですか？

A. 確認が必要です。相手先が想定しているのが FTPS（既存 FTP サーバに TLS を有効化する）である可能性があります。「SFTP（SSH・22 番）ですか、FTPS（FTP over TLS・21 番）ですか」と明示的に確認してください。SFTP であれば本ツールでそのまま対応できます。

Q. SFTP のほうがセキュリティが高いのですか？

A. 暗号の強度としては同等です。本ツールが SFTP を選んだのは、社内基準・連携先要件・ファイアウォール運用・鍵管理の簡潔さといった運用面の理由です（5 章）。ただし、比較対象が平文 FTP であれば、SFTP のほうが明確に安全です。

Q. ハッシュ検証を無効にして本当に大丈夫ですか？

A. SFTP であれば実用上の問題は小さいと判断しています。SSH がパケット単位で改ざんを検知し、書き込み・クローズ・リネームの各操作についてサーバの成功応答を確認しているためです。一方、平文 FTP では転送レイヤーに完全性の保証がないため、ハッシュ検証の有効化を推奨します。

Q. FTPS への対応予定はありますか？

A. 現時点で予定はありません。FTPS でしか接続できない連携先が出てきた場合に、要件を確認のうえ個別に検討します（6 章）。

Q. ポート 22 が開けられない場合は？

A. 社内 LAN の共有フォルダが宛先であれば Mode: "local" が使えます。外部連携で 22 番が開けられない場合は、ネットワーク・セキュリティ担当と個別にご相談ください。
