## 1. 背景
### なぜ既存ツールを作り直すのか

---

## 現状: 既存ツール FileTransFTP

社内のファイル連携は、以前から **FileTransFTP** が担ってきました。
長年の実績がある一方で、次の課題を抱えています。

- **.NET Framework 3.5** 製で技術基盤が古く(レガシー)、**改修や保守が年々難しくなっている**
- **対応プロトコルは FTP / CIFS のみで、SFTP が使えない**(CIFS は社内 LAN 向け。外部連携は平文 FTP 一択)
- 連携先から「SFTP にしてほしい」という要望が来ても応えられない
- **並列処理がなく**、大量ファイル時は 1 件ずつの逐次転送になる

---

## 既存ツールを使い続けるリスク

| 観点 | リスク |
|---|---|
| **セキュリティ** | FTP は ID・パスワード・データが**暗号化されずに流れる**。監査・セキュリティ要件で指摘される可能性 |
| **社内ルール** | 新規サーバ構築時のセキュリティ基準が厳格化。**FTP の利用には「セキュリティ除外申請」が必要**になり、構築のたびに申請・承認の負荷がかかる(SFTP なら申請不要) |
| **連携先要件** | **SFTP 必須の連携先と接続できず**、新規・更改案件で選択肢を失う |
| **保守性** | .NET Framework 3.5 等のレガシー基盤のため改修コストが高く、**対応できる要員も減っていく** |
| **将来性** | 修正のたびにリスクが増し、**塩漬けが進むほど移行が難しくなる** |

> 「動いているから触らない」を続けるほど、移行コストとリスクは膨らみます。
> 加えて**新規サーバではセキュリティ向上のため FTP に除外申請が要る**運用になりつつあり、
> **SFTP が使える後継ツールへ計画的に置き換える**のが本提案です。

## 2. 概要
### FtpTransferAgent とは何か

---

## 一言でいうと

> **現行ツール FileTransFTP の後継。
> FTP に加えて SFTP に対応し、「正しく送れたこと」の確認まで自動化した転送ツール**

- **既存ツールの役割(フォルダのファイルを定期転送)はそのまま引き継ぐ**
- .NET 10 製のコンソールアプリ(Windows / Linux / macOS で動作)
- 起動すると **1 回処理して終了する「バッチ型」**(常駐しません)
- 定期実行はタスクスケジューラ / cron に任せる設計 — **運用モデルは従来と同じ**

![w:760 ローカルフォルダ → FtpTransferAgent → FTP/SFTP サーバー の概要図](images/overview.svg)

- **アップロード(put)** / **ダウンロード(get)**

- **ハッシュ検証**(SHA256 / SHA512)
- 自動リトライ(指数バックオフ)

- 二重起動防止(ロックファイル)

### 監視・証跡
- ローリングファイルログ(保持日数指定可)
- **エラー時のメール通知**
- 終了コードでジョブ監視と連携

## 既存ツールとの比較

<style scoped>

table th, table td { padding: 0.18em 0.5em; }
blockquote { font-size: 0.78em; }
</style>

| 観点 | FileTransFTP(既存) | FtpTransferAgent(新) |
|---|---|---|
| 対応プロトコル | FTP / CIFS | **FTP + SFTP + ローカル/UNC共有** |
| セキュリティ | 平文通信(SFTP 非対応) | **暗号化・鍵認証・ホスト鍵検証** |
| 転送後の確認 | なし(送信のみ) | **ハッシュ検証(SHA256/512)** |
| 失敗時 | 自動リトライ + メール通知 | リトライ(**指数バックオフ**)+ メール通知 |
| 並列処理 | なし(1 件ずつ逐次) | **最大 16 並列・接続再利用** |
| 複数宛先配信 | 対応(再送あり/方式は非公開) | **ファンアウト + 配信トラッキング(指紋検知・宛先別並列)** |
| 技術基盤 / 配置 | .NET Framework 3.5(レガシー・要ランタイム) | **.NET 10(現行 LTS)・単一ファイル同梱** |
| 案件ごとの違い | 設定ファイル 1 つ | 設定ファイル 1 つで吸収 |

> 失敗時の「リトライ + メール通知」は両ツールとも備えます。新ツールの主な強化点は
> **SFTP・ハッシュ検証・並列処理・配信トラッキング・単一ファイル配置**です。

## 3. 動作の流れ
### 中で何が起きているのか

---

## 実行から終了までの 7 ステップ

```
 起動
  │
  ├─ ① 設定読み込み + 妥当性チェック(おかしければ即終了)
  ├─ ② 転送対象ファイルの列挙(ローカル or リモート)
  ├─ ③ フィルタ適用(拡張子 / ワイルドカード / END 条件)
  ├─ ④ 並列転送(1〜16 並列、一時名で送って完了後リネーム)
  ├─ ⑤ ハッシュ検証(送ったものが壊れていないか確認)
  ├─ ⑥ クリーンアップ(設定に応じて元ファイル等を削除)
  └─ ⑦ ログ出力して終了(成功: 0 / 失敗あり: 1)
```

> ポイント: **「送って終わり」ではなく「検証して終わり」**。
> 検証に失敗したファイルは成功扱いになりません。

---

## put と get(転送の向き)

<div class="columns">
<div>

### put(アップロード)
ローカル → リモート

```
[社内サーバー]          [連携先]
 ./watch/ ─────────▶  /remote/
  data.csv   送信      data.csv
```

- 社内で作ったデータを連携先に渡す
- 成功後にローカル削除も可能

</div>
<div>

### get(ダウンロード)
リモート → ローカル

```
[連携先]               [社内サーバー]
 /remote/ ─────────▶   ./watch/
  data.csv   取得       data.csv
```

- 連携先が置いたデータを取り込む
- 成功後にリモート削除も可能

</div>
</div>

設定ファイルの `Direction` を `"put"` / `"get"` と書き分けるだけで切り替えられます。

---

## 「バッチ型」という設計

FtpTransferAgent は**常駐しません**。起動 → 処理 → 終了、を毎回繰り返します。

```
 8:00  ──▶ 起動・転送・終了(数秒〜数分)
 8:05  ──▶ 起動・転送・終了
 8:10  ──▶ 起動・転送・終了   ← タスクスケジューラ / cron が起動
  …                              FtpTransferAgent は「呼ばれたら働く」
```

**この設計のメリット**

- プロセスが残らないので、**メモリリークや「いつの間にか止まっていた」が起きにくい**
- ジョブ管理基盤(JP1 / タスクスケジューラ / cron)に**そのまま載る**
- 失敗してもプロセスごとやり直せるので**復旧が単純**

## 4. 安心して使える理由
### 信頼性・安全性の仕組み

---

## 仕組み①: 中途半端なファイルを相手に見せない

転送中のファイルを連携先が誤って処理しないよう、**一時ファイル名**で転送します。

```
転送中:   /remote/data.csv.tmp_xxxx   ← 相手のバッチは拾わない名前
   ↓ 転送完了 + 検証 OK
完了後:   /remote/data.csv            ← この瞬間に初めて「正式な名前」になる
```

- リネームは一瞬で終わる操作なので、**「半分だけ書かれた data.csv」は存在しない**
- 連携先には「正式名のファイルだけ処理してください」と伝えればよい

> ファイル連携トラブルの定番「転送中ファイルの取り込み事故」を構造的に防ぎます。

---

## 仕組み②: ハッシュ検証

「送れた」ではなく「**壊れずに送れた**」を確認します。

```
ローカルの data.csv  ──▶ SHA256 計算 ──▶  a1b2c3...
                                              ↕ 一致するか比較
リモートの data.csv  ──▶ SHA256 計算 ──▶  a1b2c3...
```

- アルゴリズムは **SHA256 / SHA512** から選択(MD5 は安全性の理由で禁止)
- 不一致なら**そのファイルは失敗扱い** → リトライ or エラー通知
- 検証に通るまで「成功後の削除」は行われない(**消してから気づく事故がない**)

---

## 仕組み③: かしこい自動リトライ

エラーには「待てば直るもの」と「待っても直らないもの」があります。
FtpTransferAgent はこれを**自動で見分けて**振る舞いを変えます。

| エラーの種類 | 例 | 動作 |
|---|---|---|
| **一時的なエラー** | ネットワーク瞬断、タイムアウト | **自動リトライ**(間隔を倍々に広げる) |
| **恒久的なエラー** | パスワード間違い、設定ミス | **即失敗**(無駄なリトライをしない) |

- リトライ回数・間隔は設定で調整可能(既定: 3 回、5 秒から指数バックオフ)
- 「認証エラーなのに 3 回リトライして相手にアカウントロックをかける」ような事故を防ぐ

---

## 仕組み④: セキュリティへの配慮

| 機能 | 内容 |
|---|---|
| **SFTP 対応** | 通信が暗号化される転送方式。**社内では SFTP を推奨** |
| **秘密鍵認証** | パスワードより安全な鍵ファイルでのログインに対応 |
| **ホスト鍵検証** | 接続先サーバーの「指紋」を照合し、**なりすましサーバーを検出** |
| **パストラバーサル対策** | 不正なファイルパスでフォルダ外に書き込まれることを防止 |
| **起動時の警告** | 平文 FTP 使用時や検証スキップ時に警告を表示 |

> FTP(暗号化なし)も使えますが、起動時に警告が出ます。
> 新規案件では SFTP + 鍵認証 + ホスト鍵検証の組み合わせを標準としてください。

## 5. 便利機能
### 実運用を支える機能

---

## END ファイル制御とは

ファイル連携の定番プロトコル「**データを置き終わったら、目印ファイル(END)を置く**」に対応しています。

```
連携元の置き方:
  data_20260612.csv        ← データ本体(書き込みに時間がかかる)
  data_20260612.csv.END    ← 書き終わった合図(0バイトでOK)

FtpTransferAgent の動き(RequireEndFile: true):
  END がある data だけを転送する = 書きかけのデータを拾わない
```

- END ファイル自体を転送するか・しないかも選べる
- 必ず「**データ → END**」の順で転送(順序を保証するので、受け手も同じ方式を安全に使える)
- 拡張子は `.END` `.TRG` など複数指定可能

---

## END ファイル制御の動作イメージ

```
 watch フォルダ                     転送されるもの
 ├─ A.csv        + A.csv.END  ──▶  ✅ A.csv (→ 続けて A.csv.END)
 ├─ B.csv        (ENDなし)    ──▶  ⏸ スキップ(まだ書き込み中かも)
 └─ C.csv.END    (データなし) ──▶  ⏸ スキップ(対応データがない)
```

<div class="placeholder">
可能であれば、ここに<b>実際の watch フォルダのスクリーンショット</b>
(END ありのファイルと END なしのファイルが混在した状態)と、
<b>その実行ログ</b>のキャプチャを並べると説得力が出ます。<br>
撮影手順: テスト環境で上記 3 パターンのファイルを置いて 1 回実行するだけです。

## 複数宛先への同時配信(ファンアウト)

<style scoped>
li { line-height: 1.3; margin: 0.12em 0; }
p { margin: 0.4em 0; }
blockquote { font-size: 0.85em; padding: 0.35em 0.8em; margin: 0.5em 0; }
</style>

1 つのファイルを**メイン宛先 + 追加宛先のすべてへ同時に送信**できます(put のみ)。

![w:600 複数宛先への同時配信（ファンアウト）の図](images/fanout-overview.svg)

- 宛先ごとに **プロトコル・認証・並列数を個別設定**できる(**SFTP と FTP の混在も可**)
- **全宛先に成功したときだけ**ローカルファイルを削除(1 つでも失敗したら消さずに残す)
- 同じ場所(host/path)へ重複して送る誤設定は**起動時に警告**

> 用途例: 本番 + バックアップサイト、複数拠点(大阪 / 東京)への一斉配信。
> サーバー移設で**新旧サーバーへ一時的に二重送信**したい、といった用途にも使えます。

---

## 宛先がダウンしても「賢く」再送する(配信トラッキング)

<style scoped>
li { line-height: 1.3; margin: 0.12em 0; }
p { margin: 0.4em 0; }
blockquote { font-size: 0.85em; padding: 0.35em 0.8em; margin: 0.5em 0; }
</style>

複数宛先配信では、**どの宛先まで送れたかをファイル単位で記録**します。
一部の宛先が落ちていても、次回は**まだ送れていない宛先にだけ**送り直します。

![w:540 宛先がダウンしても未配信の宛先だけ再送する配信トラッキングの図](images/delivery-tracking.svg)

- **配信済みの宛先へは二重配信しない**(重複送信事故を防ぐ)
- 送信後に元ファイルが差し替わったら**指紋(サイズ+更新時刻 / ハッシュ)で検知**し、全宛先へ送り直す(静かなデータ欠落を防止)
- この記録は**部分失敗したときだけ**作られる — **全宛先成功なら追加コストはゼロ**

> 「1 拠点が落ちても、他拠点へ二重送信せず、復旧後その拠点だけ送る」を自動化。

---

## 並列処理で「速く・止まらず」送る

<style scoped>
li { line-height: 1.28; margin: 0.1em 0; }
p { margin: 0.35em 0; }
blockquote { font-size: 0.82em; padding: 0.3em 0.8em; margin: 0.45em 0; }
</style>

大量のファイルも **最大 16 並列**で同時転送できます(`Concurrency`)。ただ速いだけでなく、**並列でも壊れない**ことを重視した設計です。

![w:560 作る人・待ち行列・担当に分けた並列転送の流れ作業の図](images/parallel-pipeline.svg)

- **ワーカー隔離** — 1 ファイルの失敗が他の転送を巻き込まない(失敗分だけエラー記録)
- **接続の再利用** — 1 ファイルごとに繋ぎ直さず接続を使い回し、確立コストを削減
- **宛先ごとに並列数を指定** — 速い宛先は多めに、弱い宛先は控えめに、と個別調整
- **宛先間が独立** — ある宛先が詰まっても、健全な宛先への送信は止まらない

> 「並列で速く」かつ「1 つの失敗・遅延が全体を巻き込まない」を両立しています。

## 二重起動防止

「5 分おきに実行」していて前回がまだ終わっていなかったら…?
→ **ロックファイル(PID 方式)で自動的に防ぎます。**

```
 8:00 起動 ──▶ ロック取得 ──▶ 大きいファイルを転送中…(まだ終わらない)
 8:05 起動 ──▶ ロックあり + 前プロセス生存 ──▶ 何もせず終了(終了コード 2)
 8:10 起動 ──▶ 前回が終わっていれば通常どおり実行
```

- 同じファイルを 2 つのプロセスが同時に送る事故を防止
- 前回が**異常終了(クラッシュ)していた場合は自動で検知してロックを引き継ぐ**ので、運用者がロックファイルを手で消す必要はありません

## 6. 導入と移行
### 使い始めるには・旧ツールからどう切り替えるか

---

## 導入はファイル 2 つだけ

サーバーに置くのは基本的にこれだけです。

```
 /opt/ftp-transfer-agent/          ← 任意の配置先
 ├─ FtpTransferAgent(.exe)         ← 実行ファイル(自己完結ビルド)
 └─ appsettings.json               ← 設定ファイル
```

- **自己完結ビルド**なら、サーバーに .NET のインストールは**不要**
- Windows Server / Linux / macOS いずれも可
- プログラムの修正は不要。**案件ごとの違いは設定ファイルだけ**で吸収
- 将来 .NET 10 のサポートが終了しても、**ターゲットを次期 LTS に変えて再ビルドするだけ**で移行可能 — FileTransFTP の .NET Framework 3.5 のような作り直しは不要

> 「実行ファイル + 設定 1 枚」というシンプルさが、案件横展開のしやすさにつながっています。

---

## 設定ファイルの読み方(全体像)

`appsettings.json` は役割ごとのセクションに分かれています。

| セクション | 決めること | 例 |
|---|---|---|
| `Watch` | **何を**転送するか | フォルダ、拡張子、END 条件 |
| `Transfer` | **どこへ・どうやって**送るか | FTP/SFTP、put/get、接続先、並列数 |
| `Retry` | 失敗したら**どう粘るか** | 回数、間隔 |
| `Hash` | **どう検証するか** | SHA256 / SHA512 |
| `Cleanup` | 成功後に**消すかどうか** | ローカル削除、リモート削除 |
| `Smtp` | 障害を**誰に知らせるか** | 通知先メールアドレス |
| `Logging` | 記録を**どう残すか** | ログパス、保持日数 |

---

## 設定例: 最小構成(FTP アップロード)

```json
{
  "Watch":    { "Path": "./watch", "AllowedExtensions": [".csv"] },
  "Transfer": {
    "Mode": "ftp",  "Direction": "put",
    "Host": "ftp.example.com", "Port": 21,
    "Username": "user", "Password": "********",
    "RemotePath": "/upload"
  },
  "Retry":    { "MaxAttempts": 3, "DelaySeconds": 5 },
  "Hash":     { "Enabled": true, "Algorithm": "SHA256" }
}
```

> `./watch` フォルダの CSV を `/upload` へ送り、SHA256 で検証。
> 失敗したら 5 秒 → 10 秒 → 20 秒の間隔で 3 回までリトライ。

---

## 設定例: 推奨構成(SFTP + 鍵認証)

```json
{
  "Transfer": {
    "Mode": "sftp", "Direction": "put",
    "Host": "sftp.example.com", "Port": 22,
    "Username": "user",
    "PrivateKeyPath": "./id_ed25519",
    "HostKeyFingerprint": "SHA256:ohD8VZEXGWo6Ez8GSEJQ9Wpafg...",
    "RemotePath": "/in"
  }
}
```

**新規案件はこの形を標準に:**

- `Mode: sftp` … 通信を暗号化
- `PrivateKeyPath` … パスワードではなく秘密鍵で認証
- `HostKeyFingerprint` … 接続先が本物のサーバーか検証(なりすまし対策)

## 運用時の監視ポイント

ジョブ管理基盤からは**終了コード**で成否を判定できます。

| 終了コード | 意味 | 対応 |
|---|---|---|
| `0` | 全件成功(または対象なし) | 対応不要 |
| `1` | 設定エラー、または転送失敗あり | **ログを確認して原因対応** |
| `2` | 二重起動を検出してスキップ | 頻発するなら実行間隔を見直し |

日常の確認はこの 3 点です。

1. ジョブの終了コード(ジョブ管理基盤のアラート)
2. エラー通知メール(Smtp 有効時)
3. ログファイル(`logs/yyyy/MM/` 配下)

## 旧ツールからの移行の進め方(案)

<style scoped>
li { line-height: 1.28; margin: 0.1em 0; }
p { margin: 0.35em 0; }
pre { margin: 0.5em 0; }
.placeholder { font-size: 0.76em; padding: 0.75em 1.1em; margin: 0.4em 0; }
</style>

**転送経路(送り先・ポート・パス)は変えず、動かすツールだけを差し替える**移行です。
経路が変わらないので一斉切り替えは不要 — **影響の小さい連携から 1 件ずつ、様子を見ながら**広げられます。

```
 ① 影響の小さい連携を選ぶ   社内間連携など、止まっても影響が小さいものから
 ② 設定を移植する           送り先・ポート・パスはそのまま → 経路は変わらない
 ③ 差し替えて様子を見る     起動先を新ツールへ変更し、ログ・終了コードで結果を確認
 ④ 問題なければ次へ広げる   安定を確認できた連携から、順に同じ手順で置き換え
```

- 運用モデル(スケジューラ起動のバッチ)は従来と同じなので、**変更は起動コマンドの差し替えが中心**
- まず **FTP のまま**置き換え、**SFTP 化は連携先と調整がついた案件から**(この時だけ経路が変わる)

案件名・連携先・現行プロトコル・SFTP 化可否・移行予定時期、の5列があると意思決定に使えます。

## 7. 注意点とまとめ

---

## 注意①: 同名ファイルの上書き衝突

**唯一の「事故りやすい設定」**なので必ず押さえてください。

```
危険な組み合わせ:
  IncludeSubfolders: true   (サブフォルダも対象にする)
  PreserveFolderStructure: false  (フォルダ構造は保たない)

 watch/A/result.csv ──┐
                       ├──▶ /remote/result.csv   ← 後勝ちで上書き!
 watch/B/result.csv ──┘
```

**対策(どちらか)**

- `PreserveFolderStructure: true` にしてフォルダ構造ごと転送する(推奨)
- 全ファイルで名前が重複しない命名規約にする

※ この組み合わせでは起動時に警告も表示されます。

---

## 注意②: 向いていない用途

FtpTransferAgent は万能ではありません。以下は**別の手段**を検討してください。

| 用途 | 理由 / 代替 |
|---|---|
| リアルタイム同期(秒単位) | バッチ型のため。→ 常駐型の同期ツール |
| 双方向同期・競合解決 | 一方向転送が前提。→ 専用同期製品 |
| 人が画面で操作する転送 | CLI ツールのため。→ WinSCP 等の GUI |
| HTTP/API でのデータ連携 | FTP/SFTP 専用。→ API 連携基盤 |

> 「**フォルダに置かれたファイルを、決まった相手に、定期的に、確実に送る**」
> という用途に特化したツールです。

- **自動テストを完備**: 単体テストに加え、**実際の FTP / SFTP サーバーを立てた統合テスト**(本体を通したエンドツーエンド検証)

## まとめ

**FtpTransferAgent は、レガシー化した既存ツール FileTransFTP の後継です。**

- 置き換えの最大の動機は **SFTP 対応**(セキュリティ・連携先要件への対応)
- 単なる移植ではなく、**検証・リトライ・完了判定・証跡**も併せて強化
- 運用モデル(スケジューラ起動のバッチ)は従来と同じなので、**移行の負担は小さい**
- **設定ファイル 1 枚**で案件ごとの違いを吸収 → 段階的な置き換えがしやすい

**移行で押さえる 3 点**

1. 案件単位の**段階的置き換え**(並行稼働 → 突き合わせ → 切り替え)
2. 新規・更改案件は **SFTP + 鍵認証 + ホスト鍵検証**を標準にする
3. 移行前チェックリスト 8 項目を連携先と握る

## 付録 B: 用語集

<style scoped>
table { font-size: 0.62em; }
table th, table td { padding: 0.12em 0.5em; }
</style>

| 用語 | 意味 |
|---|---|
| **FTP / SFTP** | ファイル転送の通信方式。SFTP は暗号化あり(SSH ベース)で安全 |
| **CIFS** | Windows のファイル共有プロトコル(SMB)。主に社内 LAN 向けで、外部連携や暗号化用途には不向き |
| **put / get** | put = こちらから送る(アップロード)、get = 取りに行く(ダウンロード) |
| **ハッシュ値** | ファイル内容から計算される「指紋」。1 ビットでも違えば値が変わる |
| **END ファイル** | 「データを置き終わった」ことを示す目印ファイル。トリガーファイルとも呼ぶ |
| **ファンアウト** | 1 つのファイルを複数の宛先へ同時に配信すること(put のみ) |
| **配信トラッキング** | 複数宛先配信で「どのファイルをどの宛先まで送れたか」を記録し、未配信の宛先だけ再送する仕組み |
| **並列転送 / Concurrency** | 複数ファイルを同時に処理する数(1〜16)。1 件の失敗は他に波及しない(ワーカー隔離) |
| **指数バックオフ** | リトライ間隔を 5 秒 → 10 秒 → 20 秒のように倍々に広げる方式 |
| **バッチ型** | 常駐せず、起動のたびに 1 回処理して終了する動作モデル |
| **終了コード** | プログラムが終了時に返す数値。0 = 正常、それ以外 = 異常 |
| **ロックファイル** | 「実行中」の目印ファイル。二重起動の防止に使う |
| **.NET Framework / .NET 10** | アプリの実行基盤。Framework 3.5 は Windows 専用のレガシー。.NET 10 はクロスプラットフォームの現行 LTS(2028年まで)で、次期 LTS への移行も再ビルドで済む |
| **単一ファイル(self-contained)** | ランタイムを同梱して 1 つの実行ファイルにまとめた配布形態。サーバーに .NET を入れなくても動く |
